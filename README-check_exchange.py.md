# check_exchange.py — сканер внешних хостов на CVE-2026-62911

Пассивный (только читающий) сканер Microsoft Exchange Server для выявления признаков
уязвимости **CVE-2026-62911** в рамках **авторизованного аудита собственного периметра**.

Скрипт решает две задачи:

1. **Определение версии** Exchange по пассивным HTTP-эндпоинтам и сравнение сборки
   с таблицей закрывающих патчей.
2. **Фингерпринт MRSProxy-эндпоинта** HTTP.sys — поиск признака открытого
   релейного вектора (NTLM relay) для этой конкретной уязвимости.

> ⚠️ **Юридическое предупреждение.** Инструмент предназначен только для проверки
> систем, на которую у вас есть **письменное разрешение владельца**. Он не
> выполняет никаких эксплуатирующих действий, но даже проверка чужой инфраструктуры
> без разрешения может нарушать законодательство. Проверяйте применимость всех
> утверждений к своему окружению.

## Что это за уязвимость

**CVE-2026-62911** — *Authentication bypass by capture-replay* (CWE-294, «обход
аутентификации через перехват и повторную передачу») в Microsoft Exchange Server.

- **CVSS**: 8.0 (High) — `CVSS:3.1/AV:N/AC:L/PR:L/UI:R/S:U/C:H/I:H/A:H`
- **Суть**: HTTP.sys-вариант сервиса `MailboxReplicationProxyService` (MRSProxy)
  (`/Microsoft.Exchange.MailboxReplicationService.ProxyService`) принимает
  аутентификацию *Negotiate*, но **не проверяет channel bindings (Extended
  Protection, EPA)**. Из-за этого скомпрометированный/обманный способ релея
  NTLM-хэша машинной учётной записи (например, через PetitPotam) завершает
  аутентификацию как «локальная машина», после чего атакующий через WCF-методы
  `IMailbox_Config6()` + `IMailbox_Connect()` может записать файл (например,
  ASPX-веб-шелл) в произвольный каталог IIS и получить SYSTEM.
- **Нахождение уязвимых сборок**: уязвимыми считаются сборки *ниже* указанных
  ниже исправленных (см. [таблицу патчей](#2-логика-вердикта-по-патчам)).

> Возможность эксплуатации базируется на слабости **конфигурации** (отсутствие
> `extendedProtectionPolicy`) и **версии**. По HTTP-протоколу снаружи факт
> отсутствия EPA напрямую не виден на 100 % — скрипт даёт **косвенный признак**:
> наличие `401 + WWW-Authenticate: Negotiate` на MRSProxy-эндпоинте. Финальную
> проверку конфигурации нужно делать на сервере (см. [ограничения](#ограничения-и-важные-оговорки)).

## Быстрый старт

Если у вас установлен `uv`, проверка одного хоста выглядит так:

```bash
uv run --with rich --with requests python check_exchange.py -t exchange.contoso.com
```

Для хостов с самоподписанным сертификатом добавьте `--insecure`:

```bash
uv run --with rich --with requests python check_exchange.py -t 192.168.1.10 --insecure
```

Результат: rich-таблица по каждому эндпоинту, панель со статусом CVE-2026-62911,
общая сводка по всем хостам и текстовые отчёты в каталоге вывода.

## Установка

Есть несколько способов — выбирайте под свою среду.

### Способ 1. Через `uv` (без установки в систему)

`uv` подтянет зависимости во временное окружение и ничего не установит глобально:

```bash
uv run --with rich --with requests python check_exchange.py --help
```

### Способ 2. Через виртуальное окружение (`venv`)

```bash
python -m venv .venv
source .venv/bin/activate        # Linux/macOS
.venv\Scripts\Activate.ps1       # Windows PowerShell

pip install -r requirements.txt  # см. ниже
python check_exchange.py -t host
```

Содержимое файла `requirements.txt`:

```
requests>=2.28
rich>=13.0
```

### Способ 3. Без `rich` (минимальный вариант)

Если `rich` недоступен, скрипт всё равно работает и выводит plain-text результат:

```bash
pip install requests
python check_exchange.py -t host --plain
```

Без `rich` автоматически включается plain-режим вывода (см. `HAS_RICH`).
Флаг `--plain` форсирует его даже при установленном `rich`.

### Примеры

Проверка одного хоста:

```bash
python check_exchange.py -t mail.example.com
```

Проверка нескольких хостов сразу:

```bash
python check_exchange.py -t mail1.example.com -t mail2.example.com -t mail3.example.com
```

Проверка по списку из файла `hosts.txt` (по одному хосту на строку):

```bash
python check_exchange.py -f hosts.txt
```

Уменьшить время ожидания и проверять параллельно:

```bash
python check_exchange.py -f hosts.txt --timeout 8 --max-workers 20
```

Сохранить отчёты в отдельный каталог `reports/`:

```bash
python check_exchange.py -t mail.example.com -o reports
```

Проверка фермы за балансировщиком с самоподписанным сертификатом:

```bash
python check_exchange.py -t webmail.example.com --insecure --timeout 10
```

> Все проверки выполняются параллельно (потоки через `ThreadPoolExecutor`).
> Количество одновременных хостов регулируется флагом `--max-workers`.

## Как это работает

### Общий алгоритм

Для каждого хоста `ExchangeScanner.run()` выполняет следующие шаги:

1. Делает GET-запросы к нескольким **пассивным** эндпоинтам и сохраняет результаты
   в `TargetResult.probes` (список `ProbeResult`).
2. **Определяет сборку** Exchange в три прохода (заголовки → текст → контекст OWA).
3. Сравнивает найденную сборку с таблицей патчей и формирует **вердикт**
   (`vulnerable` / `ok` / `outdated` / `unknown`).
4. **Фингерпринтит MRSProxy**-эндпоинт и фиксирует признак `Negotiate`.
5. Складывает всё в `findings` и возвращает результат для рендера.

Ниже — детали каждого шага.

### 1. Определение версии

Эндпоинты, по которым скрипт «простукивает» сервер (все запросы — обычные `GET`):

| Эндпоинт | Назначение |
| --- | --- |
| `/owa/auth/logon.aspx` | Страница входа OWA. Часто отдаёт редирект/403, но содержит полезные заголовки. |
| `/autodiscover/autodiscover.xml` | Autodiscover-сервис. |
| `/winhttp` | WinHTTP-эндпоинт, отдаёт XML. |
| `/ews/exchange.asmx` | Exchange Web Services. |

**Порядок поиска сборки** (важно: первый совпавший вариант прекращает поиск):

- **Проход 1 — заголовки.** Сначала ищем в заголовках ответов:
  - `X-OWA-Version` (формируемый OWA-заголовок с номером сборки);
  - `X-AspNet-Version` (версия ASP.NET как дополнительный ориентир).
  Логика — функция `_find_version_in_headers()`.

- **Проход 2 — текст.** Если в заголовках версии нет, ищем в первых 4096 байтах
  тела ответа первый фрагмент вида `15.1`, `15.2`, `15.0`, `14.3`, `8.3`, `8.2`,
  за которым следует цифры и точки (функция `_find_version_in_text()`).

- **Проход 3 — контекст OWA.** Если не нашли, но тело страницы OWA содержит
  ключевые слова `microsoft exchange` / `owa` / `exchange server`, берём окно
  текста вокруг ключевого слова и ищем в нём сборку `15.x`
  (разновидность прохода 2 с привязкой к контексту).

**Определение семейства.** По найденной сборке скрипт определяет линейку:

- `15.1.*` → **Exchange 2016**
- `15.2.*` → **Exchange 2019 / Exchange SE**

Результат кладётся в `TargetResult.version_build` и `TargetResult.version_family`.

### 2. Логика вердикта по патчам

Функция `_evaluate(build)` сверяет найденную сборку с таблицей патчей
`CVE_2026_62911_PATCHES`:

| Продукт | Исправленная сборка | KB |
| --- | --- | --- |
| Exchange 2016 CU23 | `15.1.2507.72` | KB5121576 |
| Exchange 2019 CU14 | `15.2.1544.43` | KB5121575 |
| Exchange 2019 CU15 | `15.2.1748.48` | KB5121574 |
| Exchange SE RTM | `15.2.2562.45` | KB5121573 |

Алгоритм сравнения:

1. Если сборки нет → вердикт `unknown`.
2. Если сборка не распознаётся как `x.y.z.w` → вердикт `unknown`.
3. Для каждой записи таблицы: если мажорная и минорная части сборки (`x.y`)
   совпадают с записью таблицы, то:
   - сборка **меньше** исправленной → **`vulnerable`**;
   - сборка **больше или равна** исправленной → **`ok`**.
4. Если ни одна запись не подошла → вердикт **`outdated`** (ветка вне таблицы
   патчей: например, Exchange 2010/2013, или сборка не из известной линейки —
   требует ручного уточнения).

> **Важная оговорка о сравнении для 15.2.** Внутри ветки `15.2` разные CU имеют
> разный минорный номер, поэтому сравнение «по строкам таблицы» срабатывает
> корректно только когда мажор.минор точно совпадает с записью. Сборки, например,
> `15.2.xxxx.x`, не попавшие минором ни в одну строку, уйдут в `outdated`
> (требуют ручной проверки). Это консервативная (в сторону безопасности) логика.

### 3. Фингерпринт MRSProxy

Метод `_detect_msrs_endpoint()` обращается к уязвимому HTTP.sys-эндпоинту:

```
/Microsoft.Exchange.MailboxReplicationService.ProxyService
```

и анализирует ответ:

- Если статус `401` / `403` **и** в заголовке ответа `WWW-Authenticate` есть
  строка `negotiate` → признак открытого релейного вектора фиксируется как
  присутствующий (`TargetResult.msrs_negotiate = True`), а в `note` выводится
  пояснение.
- Если `401` / `403`, но `Negotiate` отсутствует → признак отсутствует.
- Иначе (`200`, другие коды) — выводится статус и `Server`-заголовок
  (в т.ч. пометка, отвечает ли именно `Microsoft-HTTPAPI`).

> **Ключевой нюанс.** Наличие `Negotiate` — это **обязательное, но
> недостаточное** условие. Сама по себе строка `Negotiate` в `WWW-Authenticate`
> не доказывает отсутствие Extended Protection. Снаружи по HTTP это достоверно
> не проверить. Поэтому результат фингерпринта трактуется как **сигнал к
> ручной проверке** конфигурации на самом сервере. Подробнее — в
> [ограничениях](#ограничения-и-важные-оговорки).

## Интерпретация результатов

### Вердикты

По каждому хосту выводится панель «CVE-2026-62911 — статус» с цветовой меткой:

| Вердикт | Цвет | Значение | Действие |
| --- | --- | --- | --- |
| `vulnerable` | 🔴 красный | Сборка ниже исправленной, относится к уязвимой линейке | Немедленно планировать патчи, проверить MRS-признак |
| `ok` | 🟢 зелёный | Сборка равна/выше исправленной | Обновлять по обычному циклу патчей |
| `outdated` | 🟠 оранжевый | Сборка вне таблицы патчей CVE-2026-62911 | Уточнить линейку и закрывающий патч вручную |
| `unknown` | 🟡 жёлтый | Не удалось определить сборку (нет ответа, TLS, и т.п.) | Проверить доступность хоста/эндпоинтов |

Куск в консоль в конце выводится **сводка по всем хостам** с группировкой по
статусу и счётчиками.

### Таблица эндпоинтов

После панели статуса печатается таблица «Проверка / Статус / HTTP / Server /
Версия / детали», где по каждой строке (эндпоинту) видно:

- `OK` — запрос выполнен (получен HTTP-код), `FAIL` — ошибка
  (таймаут/соединение/TLS);
- фактический HTTP-код;
- значение заголовка `Server`;
- значение `X-OWA-Version` либо текст ошибки.

## Ограничения и важные оговорки

1. **Это косвенный признак, а не доказательство.** Скрипт проверяет версию и
   наличие `Negotiate` на MRSProxy. Отсутствие **Extended Protection** снаружи
   достоверно не детектируется — его надо проверять на сервере.
2. **Фингерпринт версии не всегда возможен.** Некоторые прокси/балансировщики
   скрывают заголовки, а страницы могут отдаваться за кэшем. Тогда вердикт будет
   `unknown`.
3. **Только чтение.** Инструмент выполняет обычные `GET`-запросы без аутентификации
   и не содержит эксплуатирующего кода. Он не проверяет *фактическую* возможучаство
   релея, а лишь отмечает предпосылки.
4. **Авторизация обязательна.** Использование против систем без разрешения
   нарушает законодательство. Вы несёте ответственность за соблюдение рамок
   разрешённого тестирования.
5. **База патчей консервативна.** Сборки, не попавшие минором в таблицу, помечаются
   `outdated` и требуют ручной проверки. Это сделано намеренно — чтобы не ошибиться
   в сторону ложного «OK».

## Структура кода (обзор)

| Фрагмент | Ответственность |
| --- | --- |
| `CVE_2026_62911_PATCHES` | Таблица продуктов, исправленных сборок и KB. |
| `ProbeResult` | Результат одного HTTP-проступа к одному эндпоинту. |
| `TargetResult` | Агрегированный результат по хосту (версия, фингерпринт, findings). |
| `_find_version_in_headers()` | Поиск сборки в заголовках ответа. |
| `_find_version_in_text()` | Поиск сборки в теле ответа по сигнатурам версий. |
| `_version_tuple()` | Перевод строки `x.y.z.w` в кортеж чисел для сравнения. |
| `_evaluate()` | Сопоставление сборки с таблицей патчей → вердикт. |
| `ExchangeScanner` | Выполнение HTTP-запросов (`_get`), сканирование эндпоинтов, их разбор. |
| `ExchangeScanner._detect_msrs_endpoint()` | Фингерпринт MRSProxy (401 + Negotiate). |
| `render_one()` / `render_result_plain()` | Вывод в консоль (rich или plain) и в файл. |
| `main()` | Разбор CLI, параллельный запуск воркеров, сводка, сохранение отчётов. |

**Параллельность.** Хосты обрабатываются в пуле потоков `ThreadPoolExecutor`
(размер = `--max-workers`). Каждый поток строит свой `requests.Session`, поэтому
совместное использование соединений между хостами не происходит.

## Рекомендации по защите (митигация)

Если ресурсы подтверждают, что среда уязвима или есть признаки открытого
MRSProxy-вектора:

1. **Установить обновления** (первоочередное):
   - Exchange 2016 CU23 → KB5121576;
   - Exchange 2019 CU14 → KB5121575;
   - Exchange 2019 CU15 → KB5121574;
   - Exchange SE → KB5121573.
   > Exchange 2016 EOL (октябрь 2025) — обновление только через Extended
   > Security Updates (ESU); если ESU не куплены, патча нет — планируйте
   > миграцию/вывод из эксплуатации.
2. **Проверить и включить Extended Protection (EPA)** на HTTP.sys-варианте
   MRSProxy. Убедиться, что в
   `%ExchangeInstallDir%\Bin\MSExchangeMailboxReplication.exe.config` для
   биндинга `MrsProxyHttpsBinding` задан `extendedProtectionPolicy`, а не
   только `authenticationScheme="Negotiate"`.
3. **Ограничить доступ** к эндпоинту
   `/Microsoft.Exchange.MailboxReplicationService.ProxyService` снаружи
   (только внутренние/доверенные источники; через ограничивающие правила
   брандмауэра/WAF).
4. **Отслеживать NTLM-релеи.** Смотреть на источник `PetitPotam`
   (`EfsRpcOpenFileRaw` / MS-EFSR) и аномальные `Negotiate`-аутентификации.
5. **Ограничить право `ms-Exch-EPI-Token-Serialization`** у машинных учётных
   записей, если это допустимо в вашей среде (с осторожностью — влияет на флоу).

## Известные несоответствия документации и кода

При работе с этим скриптом учитывайте, что часть комментариев в исходнике и
старой справке отсылает к **нереализованным** возможностям:

- В шапке файла и `--help`-описании упоминается `/rpc`, но фактических обращений
  к `/rpc`, `/ecp`, `/oab`, `/microsoft-server-activesync` в коде **нет** — они лишь
  константы для будущего расширения.
- В шапке файла упомянут флаг `--list-hosts`, однако в CLI его **нет** (список хостов
  задаётся флагом `-f`).
- В коде есть импорт `requests_ntlm` и упоминание `--auth ntlm sцсц`, но такого
  аргумента в CLI **нет** — код не производит NTLM-аутентификации и релея
  (и не должен: инструмент пассивный).
- Функция `_find_patch()` объявлена, но в текущем сценарии **не вызывается** —
  всю логику сопоставления выполняет `_evaluate()`. Функция зарезервирована под
  более точный выбор конкретного патча.

Это сделано непреднамеренно при первом написании; при доработке скрипта стоит
привести документацию в соответствие с фактическим поведением (или добавить
упомянутые возможности).
